# Robot Voice Session Integration

## Configuration

Set the robot client's HTTP base URL on the transit server:

```env
ROBOT_CLIENT_BASE_URL=http://localhost:9000
ROBOT_CLIENT_TIMEOUT_MS=5000
ROBOT_ID=4
```

If `ROBOT_CLIENT_BASE_URL` is omitted, the project defaults to `http://localhost:9000` for the current same-server deployment.

The robot client must therefore listen on `localhost:9000`, `127.0.0.1:9000`, or `0.0.0.0:9000`. Binding the robot client only to a specific LAN address does not guarantee that `localhost:9000` will be reachable. If the two services later run in separate containers, replace `localhost` with the robot client's container service name or another reachable address.

The browser never calls the robot client directly. The transit server forwards the control request so the robot address stays out of browser code and cross-origin restrictions do not apply.

## Whole-session control

The page calls the internal endpoint:

```http
POST /api/voice-session/control
```

On the first microphone click:

```json
{
  "status": "1"
}
```

The transit server generates a whole-session ID and forwards this request to the robot client:

```http
POST http://<robot-client>:9000/robot/voiceSession/control
```

```json
{
  "robotId": "4",
  "sessionId": "session-<uuid>",
  "status": "1"
}
```

The returned `sessionId` stays unchanged until the second click. Silence and `POST /robot/voiceMonitor` do not end this whole session.

On the second microphone click, the page sends the stored ID:

```json
{
  "sessionId": "session-<uuid>",
  "status": "0"
}
```

The transit server injects the configured `ROBOT_ID` when forwarding both commands. After a successful stop, it marks that voice session closed and clears its active model-response accumulator and snapshot. Existing messages remain visible in the page.

## Robot model callbacks

The robot client reports its Qwen response to the transit server with three phases.

The required order is:

```text
response_monitor status="1"
  -> zero or more Response/stream increments
  -> response_monitor status="0"
```

The callback `robotId` must equal the configured `ROBOT_ID`, and `sessionId` must identify that robot's current whole voice session. Immediate duplicate starts and callbacks received before start, after response completion, or for another robot or session return HTTP 200 with `ignored: true` and are not shown. If a previous response already produced content but its completion callback was lost, a later start closes that interrupted response and opens a new one instead of merging their text.

Start:

```http
POST /robot/model/response_monitor
```

```json
{
  "robotId": "4",
  "sessionId": "session-<uuid>",
  "status": "1"
}
```

Each incremental fragment:

```http
POST /robot/model/Response/stream
```

```json
{
  "robotId": "4",
  "event": "RESPONSE_PARTIAL",
  "language": "CN",
  "sessionId": "session-<uuid>",
  "content": "今天"
}
```

`content` is an incremental fragment, not the accumulated response. The transit server publishes each fragment to `GET /robot/events`, and the page appends it to the current assistant message. The server also maintains one bounded cumulative snapshot for each active model response. Opening or reconnecting the page during generation replaces the displayed content with this authoritative snapshot before later live fragments continue; completed or manually stopped responses do not retain an active snapshot.

Completion:

```http
POST /robot/model/response_monitor
```

```json
{
  "robotId": "4",
  "sessionId": "session-<uuid>",
  "status": "0"
}
```

These callbacks use the whole-session ID generated by the transit server. The ASR client's per-utterance `sessionId` remains separate and is used only by the existing `ASR_PARTIAL` flow.

## Testing

Start the transit server with the robot client URL configured, then use the page microphone button. For direct callback checks, first start a page session and copy its returned ID from the browser network response or server log:

```bash
curl -X POST http://localhost:4000/robot/model/response_monitor \
  -H "Content-Type: application/json" \
  -d '{"robotId":"4","sessionId":"session-<uuid>","status":"1"}'

curl -X POST http://localhost:4000/robot/model/Response/stream \
  -H "Content-Type: application/json" \
  -d '{"robotId":"4","event":"RESPONSE_PARTIAL","language":"CN","sessionId":"session-<uuid>","content":"您好，"}'

curl -X POST http://localhost:4000/robot/model/response_monitor \
  -H "Content-Type: application/json" \
  -d '{"robotId":"4","sessionId":"session-<uuid>","status":"0"}'
```

Open the page before sending callbacks so `GET /robot/events` can render the start, incremental text, and completion in real time.
